## Branch 생성 및 운영 원칙

### 1. 기본 브랜치 구조
- `main`
  - 배포 및 최종 결과물 브랜치
  - 직접 작업
- `test`
  - 개발 통합 브랜치
  - 모든 기능 브랜치는 develop으로 병합
- `name`
  - 프론트엔드 / 백엔드 브랜치
  - 예시:
    - `woong`
    - `min`

### 2. Branch 생성 규칙
- 새로운 기능 개발 시 반드시 `test` 브랜치에서 분기
- 브랜치명은 **기능 목적이 명확하게 드러나도록 작성**
- 1 브랜치 = 1 기능 원칙


## 🔄 Commit 검토 및 피드백 협업 방식

본 프로젝트에서는 **커밋 단위 협업 피드백**을 통해  
코드 품질 유지와 팀원 간 이해도 향상을 목표로 한다.

### 1. 커밋 검토 원칙
- 팀원은 각자 커밋 후, GitLab을 통해 **다른 팀원의 커밋 내용을 확인**
- 아래 항목을 중심으로 상호 확인 진행
  - 코드 동작 여부
  - 코드 가독성
  - 기능 목적에 맞는 구현 여부
  - 불필요한 코드 또는 개선 가능 지점

### 2. 피드백 방식
- 간단한 피드백은 메신저로 공유
- 수정이 필요한 경우:
  - 해당 커밋 내용에 대한 의견 공유
  - 필요 시 추가 커밋으로 반영

### 3. 피드백 반영 흐름
1. 기능 개발 후 커밋
2. 팀원 커밋 내용 확인
3. 피드백 공유
4. 피드백 반영 커밋 추가
5. test 브랜치 병합

### 4. 협업 효과
- 기능 단위 이해도 향상
- 코드 품질 및 일관성 유지
- 협업 과정에서 발생 가능한 오류 사전 방지
